# 插件系统详解

插件系统是 Claude Code 最强大的功能之一，它允许你扩展 Claude 的能力、分享最佳实践，甚至构建可复用的产品。本章将带你从零开始开发并发布自己的插件。

---

## 一、什么是插件系统

### 1.1 基本概念

**插件（Plugin）** 是一个可扩展的功能包，包含：
- 📦 Hook 配置（自动化规则）
- 🤖 Agent 定义（专门助手）
- 📝 技能文档（使用指南）
- ⚙️ 配置文件（元数据）

**类比理解：**
```
Chrome 浏览器 + 扩展程序 = 增强的浏览器
    ↓
Claude Code + 插件 = 增强的 AI 编程助手
```

---

### 1.2 为什么需要插件

#### 场景 1：团队规范统一
```
问题：
- 团队成员代码风格不一致
- 安全规范执行不到位
- 新人培训成本高

解决：
✅ 开发团队规范插件
  - ESLint 自动检查
  - 安全规范 Hook
  - 最佳实践引导
```

#### 场景 2：领域知识沉淀
```
问题：
- 老员工离职，经验流失
- 相同错误重复犯
- 最佳实践未传承

解决：
✅ 开发领域知识插件
  - 金融业务规则
  - 医疗合规检查
  - 电商风控策略
```

#### 场景 3：工具链集成
```
问题：
- 多个系统切换麻烦
- 信息孤岛
- 效率低下

解决：
✅ 开发工具集成插件
  - Jira 状态同步
  - Slack 通知
  - CI/CD 触发
```

---

### 1.3 插件 vs Hook vs Agent

**关系图：**
```
插件 (Plugin)
    ├── Hook 系统 (自动化规则)
    │   ├── PreToolUse
    │   ├── PostToolUse
    │   └── Stop
    ├── Agent 系统 (专门助手)
    │   ├── code-reviewer
    │   └── security-expert
    └── 技能文档 (使用指南)
        └── SKILL.md
```

**对比表：**

| 特性 | Hook | Agent | 插件 |
|------|------|-------|------|
| **用途** | 自动化检查 | 专门任务 | 功能集合 |
| **形式** | JSON 配置 | Markdown 文件 | 完整项目 |
| **复杂度** | 低 | 中 | 高 |
| **可发布** | ✅ (通过插件) | ✅ (通过插件) | ✅ |

```bash

  "name": "code-quality-plugin",
  "version": "1.0.0",
  "description": "Code quality checker plugin with linting and best practices",
  "author": {
    "name": "Your Name",
    "email": "your.email@example.com"
  },
  "license": "MIT"
}
EOF
```

---

#### 步骤 3：创建 Hook 配置

```bash
cat > hooks/hooks.json << 'EOF'
{
  "description": "代码质量检查 Hook",
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "bash ${CLAUDE_PLUGIN_ROOT}/scripts/check-code-quality.sh",
            "timeout": 15
          }
        ]
      }
    ]
  }
}
EOF
```

---

#### 步骤 4：创建检查脚本

```bash
cat > hooks/scripts/check-code-quality.sh << 'EOF'
#!/bin/bash
set -euo pipefail

# 读取输入
input=$(cat)
file_path=$(echo "$input" | jq -r '.tool_input.file_path // ""')
content=$(echo "$input" | jq -r '.tool_input.content // ""')

# 只检查 TypeScript/JavaScript 文件
if [[ ! "$file_path" =~ \.(ts|js)$ ]]; then
  exit 0
fi

# 检查项 1：函数长度
long_functions=$(echo "$content" | grep -E "^function\s+\w+\s*\(" | wc -l)
if [ "$long_functions" -gt 0 ]; then
  echo "⚠️  检测到长函数，建议拆分为小函数" >&2
fi

# 检查项 2：TODO 注释
todo_count=$(echo "$content" | grep -i "// TODO" | wc -l)
if [ "$todo_count" -gt 3 ]; then
  echo "⚠️  发现 $todo_count 个 TODO 注释，建议及时清理" >&2
fi

# 检查项 3：console.log
console_count=$(echo "$content" | grep "console.log" | wc -l)
if [ "$console_count" -gt 0 ]; then
  echo "⚠️  发现 $console_count 个 console.log，生产环境应该移除" >&2
fi

# 通过检查
exit 0
EOF

chmod +x hooks/scripts/check-code-quality.sh
```

#### 步骤 5：创建 Agent

```bash
cat > agents/code-quality-advisor.md << 'EOF'
---
name: code-quality-advisor
description: 代码质量顾问，提供重构建议和最佳实践指导
model: inherit
color: blue
tools: ["Read", "Grep"]
---

你是经验丰富的代码质量顾问。

**你的核心职责：**
1. 识别代码异味（Code Smell）
2. 提供重构建议
3. 推广最佳实践
4. 提高代码可维护性

**审查维度：**

### 1. 单一职责原则
- 函数是否只做一件事
- 类是否有明确的职责

### 2. 命名规范
- 变量名是否有意义
- 函数名是否动词开头
- 类名是否名词

### 3. 代码复用
- 是否有重复代码
- 是否可以提取公共函数

### 4. 可测试性
- 是否依赖注入
- 是否纯函数优先

**输出格式：**
```markdown
## 代码质量报告

### 📊 整体评分：85/100

### ✅ 优点
1. 良好的模块化设计
2. 充分的注释说明
3. 一致的命名风格

### ⚠️ 改进建议

#### 优先级：高
1. **函数过长** - UserService.ts:45
   - 当前：120 行
   - 建议：拆分为 createUser(), validateUser(), hashPassword()

#### 优先级：中  
1. **重复代码** - OrderService.ts 和 CartService.ts
   - 都有价格计算逻辑
   - 建议：提取为 PriceCalculator 类

#### 优先级：低
1. **命名优化** - 变量 d 改为 daysUntilExpiry
```
EOF
```

# 代码质量分析技能

## 何时使用此技能

当你需要：
- 评估代码质量
- 识别重构机会
- 学习最佳实践
- 准备代码审查

### 方式 1：直接询问
```

```

## 分析维度

### 1. 代码复杂度
- 圈复杂度 < 10
- 认知复杂度 < 15

### 2. 代码重复率
- 重复代码 < 5%
- 相似代码 < 10%

### 3. 测试覆盖率
- 单元测试 > 90%
- 关键路径 100%

### 4. 文档完整性
- 公共 API 有 JSDoc
- 复杂逻辑有注释

## 评分标准

| 分数 | 等级 | 说明 |
|------|------|------|
| 90-100 | A+ | 优秀，可直接上线 |
| 80-89 | A | 良好，少量改进 |
| 70-79 | B | 中等，需要优化 |
| 60-69 | C | 及格，建议重构 |
| < 60 | D | 较差，必须重构 |

### 待改进
⚠️ 3 个函数超过 50 行  
⚠️ 部分代码重复  
⚠️ 缺少类型定义  

### 具体建议
1. 拆分 createUser 函数（当前 89 行）
2. 提取验证逻辑到 Validator 类

```

### ✅ 推荐做法

1. **从小做起**
   - 先实现核心功能
   - 逐步迭代完善
   - 避免过度设计

2. **充分测试**
   - 单元测试覆盖
   - 集成测试验证
   - 真实场景测试

3. **详细文档**
   - README 清晰
   - 使用示例丰富
   - FAQ 完备

4. **持续维护**
   - 及时修复 Bug
   - 收集用户反馈
   - 定期更新

### ❌ 避免的错误

1. **钩子过多过滥**
   ```
   ❌ 每个操作都检查 → 用户体验极差
   ✅ 关键节点检查 → 平衡质量和效率
   ```

2. **性能糟糕**
   ```
   ❌ 每个 Hook 执行 10 秒+
   ✅ 优化到 1 秒内
   ```

3. **文档缺失**
   ```
   ❌ 只有代码
   ✅ 代码 + 文档 + 示例
   ```
