## 一、分层架构设计

### 1.1 为什么需要分层？

**问题场景**：

```bash
my-plugin/
├── commands/
│   ├── build.md          # 调用脚本
│   ├── test.md           # 又调用同样的脚本
│   └── deploy.md         # 还是调用同样的脚本
├── agents/
│   └── builder.md        # 也调用脚本
└── hooks/
    └── scripts/
        └── build.sh      # 所有地方都调用这个脚本
```

**问题**：
- ❌ 逻辑分散，难以维护
- ❌ 重复代码多
- ❌ 修改一处影响全局
- ❌ 新人难以理解

**解决方案**：分层架构

---

### 1.2 四层架构模型

```
┌─────────────────────────────────────┐
│     Presentation Layer (表现层)      │
│  - Commands (用户接口)               │
│  - Agents (任务协调)                 │
└─────────────────────────────────────┘
              ↓ calls
┌─────────────────────────────────────┐
│     Business Logic Layer (业务层)    │
│  - Skills (领域知识)                 │
│  - Core Services (核心服务)          │
└─────────────────────────────────────┘
              ↓ uses
┌─────────────────────────────────────┐
│    Data Access Layer (数据访问层)    │
│  - MCP Servers (外部服务)            │
│  - Database Connectors               │
└─────────────────────────────────────┘
              ↓ depends on
┌─────────────────────────────────────┐
│   Infrastructure Layer (基础设施)    │
│  - Utils (工具函数)                  │
│  - Helpers (辅助函数)                │
│  - Config (配置管理)                 │
└─────────────────────────────────────┘
```

---

### 1.3 各层职责详解

#### 第一层：表现层（Presentation Layer）

**职责**：与用户交互

**包含组件**：
- **Commands** - 用户主动调用的命令
- **Agents** - 自动选择的任务助手

**特点**：
- ✅ 直接面向用户
- ✅ 使用自然语言
- ✅ 格式化输出结果
- ✅ 不应该有复杂逻辑

**示例**：

```markdown
<!-- commands/build-project.md -->
---
description: 构建项目
argument-hint: [options]
---

# Build Command

使用构建服务执行构建：

!`node ${CLAUDE_PLUGIN_ROOT}/lib/core/builder.js $1`

生成报告：
## 构建结果

[显示格式化的构建输出]
```

**关键点**：Command 只负责调用核心服务，不处理构建逻辑。

---

#### 第二层：业务逻辑层（Business Logic Layer）

**职责**：实现核心功能

**包含组件**：
- **Skills** - 领域知识库
- **Core Services** - 核心业务逻辑

**特点**：
- ✅ 封装业务规则
- ✅ 提供统一接口
- ✅ 可复用
- ✅ 独立于具体命令

**示例**：

```javascript
// lib/core/builder.js
const { execAsync } = require('../utils/exec');
const config = require('../config');

async function build(options) {
  // 1. 验证配置
  validateConfig(config);
  
  // 2. 准备构建环境
  await prepareEnvironment();
  
  // 3. 执行构建
  const result = await execAsync('npm run build');
  
  // 4. 处理结果
  return processResult(result);
}

module.exports = { build };
```

**关键点**：核心逻辑可被多个 Commands/Agents 复用。

---

#### 第三层：数据访问层（Data Access Layer）

**职责**：访问外部资源

**包含组件**：
- **MCP Servers** - 外部服务集成
- **Database Connectors** - 数据库连接
- **API Clients** - API 客户端

**特点**：
- ✅ 隔离外部依赖
- ✅ 统一数据访问
- ✅ 易于 Mock 测试
- ✅ 支持多种数据源

**示例**：

```javascript
// lib/data/github-client.js
const { Octokit } = require('@octokit/rest');

class GitHubClient {
  constructor(token) {
    this.octokit = new Octokit({ auth: token });
  }
  
  async getRepository(owner, repo) {
    return this.octokit.repos.get({ owner, repo });
  }
  
  async createIssue(owner, repo, title, body) {
    return this.octokit.issues.create({ owner, repo, title, body });
  }
}

module.exports = GitHubClient;
```

**关键点**：上层不需要知道如何访问 GitHub，只需调用接口。

---

#### 第四层：基础设施层（Infrastructure Layer）

**职责**：提供通用工具

**包含组件**：
- **Utils** - 通用工具函数
- **Helpers** - 辅助函数
- **Config** - 配置管理

**特点**：
- ✅ 无业务逻辑
- ✅ 纯工具性质
- ✅ 高度可复用
- ✅ 稳定不变

**示例**：

```javascript
// lib/utils/exec.js
const { exec } = require('child_process');
const util = require('util');

const execAsync = util.promisify(exec);

async function safeExec(command, options = {}) {
  try {
    const { stdout, stderr } = await execAsync(command, {
      timeout: options.timeout || 30000,
      maxBuffer: options.maxBuffer || 10 * 1024 * 1024
    });
    
    return {
      success: true,
      stdout,
      stderr
    };
  } catch (error) {
    return {
      success: false,
      error: error.message
    };
  }
}

module.exports = { execAsync, safeExec };
```

**关键点**：提供安全、可靠的底层工具。

### 1.5 分层的好处

**对比单层架构**：

| 特性 | 单层架构 | 分层架构 |
|------|---------|---------|
| **可维护性** | ❌ 困难（牵一发而动全身） | ✅ 容易（层与层隔离） |
| **可测试性** | ❌ 困难（依赖多） | ✅ 容易（Mock 接口） |
| **可复用性** | ❌ 低（逻辑分散） | ✅ 高（核心层独立） |
| **可扩展性** | ❌ 低（难以添加） | ✅ 高（逐层扩展） |
| **学习曲线** | ❌ 陡峭（混乱） | ✅ 平缓（清晰） |

**实际收益**：
- ✅ **新人上手快** - 清晰的层次结构
- ✅ **修改风险低** - 影响范围可控
- ✅ **代码复用高** - 核心逻辑多处使用
- ✅ **团队协作好** - 每人负责不同层

**问题**：插件功能越来越多，如何组织？

**方案**：核心 + 扩展模式

```
│   │   └── core-agent.md
│   └── lib/
│       └── core-logic.js

├── extensions/                  # 扩展模块（可选）

│   │   │   ├── create-pr.md
│   │   │   └── review-code.md
```

**在代码中检查**：

```javascript
// lib/extension-loader.js
const config = require('./config');

function loadExtensions() {
  const extensions = [];
  
  for (const [name, ext] of Object.entries(config.extensions)) {
    if (ext.enabled) {
      console.log(`Loading extension: ${name}`);
      extensions.push(require(ext.path));
    } else {
      console.log(`Extension disabled: ${name}`);
    }
  }
  
  return extensions;
}
```

## 三、Plugin within Plugin 模式

### 3.1 什么是 Plugin within Plugin？

**概念**：在一个大插件内部，包含多个小插件的结构和功能。

**类比**：
```
俄罗斯套娃：
  大插件（外层）
    └── 子插件 A（内层）
    └── 子插件 B（内层）
    └── 子插件 C（内层）
```

---

### 3.2 使用场景

**场景 1：插件家族**

```
devops-toolkit/              # 主插件
├── ci-cd/                   # CI/CD 子插件
│   ├── commands/
│   ├── agents/
│   └── .mcp.json
├── monitoring/              # 监控子插件
│   ├── commands/
│   ├── agents/
│   └── .mcp.json
└── security/                # 安全子插件
    ├── commands/
    ├── agents/
    └── .mcp.json
```

**好处**：
- ✅ 统一管理
- ✅ 共享工具库
- ✅ 可选安装

---

**场景 2：渐进式功能**

```
advanced-editor/             # 主插件
├── basic/                   # 基础功能（免费）
│   ├── commands/
│   │   ├── format.md
│   │   └── lint.md
│   └── lib/
│       └── basic-tools.js
├── pro/                     # 专业功能（付费）
│   ├── commands/
│   │   ├── refactor.md
│   │   └── optimize.md
│   └── lib/
│       └── pro-tools.js
└── enterprise/              # 企业功能（定制）
    ├── commands/
    └── lib/
```

**好处**：
- ✅ 功能分级
- ✅ 按需启用
- ✅ 便于升级

### 3.4 子插件通信

**通过共享状态**：

```javascript
// lib/shared-state.js
const state = {
  currentProject: null,
  lastBuild: null,
  config: {}
};

function setState(key, value) {
  state[key] = value;
}

function getState(key) {
  return state[key];
}

module.exports = { setState, getState };
```

**子插件 A 设置状态**：

```javascript
// sub-plugins/plugin-a/lib/builder.js
const sharedState = require('../../lib/shared-state');

async function build() {
  const result = await executeBuild();
  sharedState.setState('lastBuild', result);
}
```

**子插件 B 读取状态**：

```javascript
// sub-plugins/plugin-b/lib/deployer.js
const sharedState = require('../../lib/shared-state');

async function deploy() {
  const buildResult = sharedState.getState('lastBuild');
  if (!buildResult) {
    throw new Error('No build found');
  }
  await executeDeploy(buildResult);
}
```

### 4.1 Command + Agent 协作

```markdown
3. 分类问题严重程度
4. 生成详细报告

**输出格式：**
## 代码审查报告

### 🔴 严重问题
```

## 五、性能优化实战

### 5.1 Hook 执行时间控制

**问题**：Hook 执行太慢，影响用户体验

**优化策略 1：快速失败**

```bash
#!/bin/bash

# ❌ 错误：先做复杂操作
result=$(expensive_operation)
if [[ ! -f ".claude/config.local.md" ]]; then
  exit 0  # 配置不存在，但已经浪费了时间
fi

# ✅ 正确：先快速检查
if [[ ! -f ".claude/config.local.md" ]]; then
  exit 0  # 立即退出，耗时 < 1ms
fi

# 然后再执行复杂操作
result=$(expensive_operation)
```

---

**优化策略 2：设置超时**

```json
{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit",
      "hooks": [{
        "type": "command",
        "command": "python3 check-security.py",
        "timeout": 5  // ← 5 秒超时
      }]
    }]
  }
}
```

**在 Python 脚本中**：

```python
#!/usr/bin/env python3
import signal
import sys

def timeout_handler(signum, frame):
    print("⚠️  Hook execution timeout", file=sys.stderr)
    sys.exit(1)

# 设置 5 秒超时
signal.signal(signal.SIGALRM, timeout_handler)
signal.alarm(5)

# 执行检查
check_security()

# 取消闹钟
signal.alarm(0)
```

---

**优化策略 3：缓存结果**

```python
#!/usr/bin/env python3
from functools import lru_cache
import hashlib

@lru_cache(maxsize=128)
def check_pattern(content_hash, pattern):
    """缓存检查结果"""
    # 耗时的检查逻辑
    return perform_check(content_hash, pattern)

def check_security(content):
    content_hash = hashlib.md5(content.encode()).hexdigest()
    
    # 如果内容相同，直接返回缓存结果
    if content_hash in cache:
        return cache[content_hash]
    
    result = check_pattern(content_hash, 'dangerous')
    cache[content_hash] = result
    return result
```

### 5.2 内存管理

**问题**：插件占用内存过多

**优化策略 1：流式处理**

```python
# ❌ 错误：一次性加载大文件
with open('large_file.json') as f:
    data = json.load(f)  # 可能几百 MB

# ✅ 正确：流式读取
import ijson

with open('large_file.json') as f:
    for item in ijson.items(f, 'item'):
        process(item)  # 逐条处理，不占内存
```

**优化策略 2：及时释放资源**

```python
class ResourceHandler:
    def __enter__(self):
        self.resource = acquire_resource()
        return self.resource
    
    def __exit__(self, exc_type, exc_val, exc_tb):
        release_resource(self.resource)  # 确保释放

# 使用上下文管理器
with ResourceHandler() as resource:
    use_resource(resource)
# 自动释放，不会内存泄漏
```

```
vMAJOR.MINOR.PATCH

   └─ 破坏性变更

```

