# 置信度评分机制

> **重要提示**：置信度评分是 Claude Code 质量保障的核心机制。通过量化评估每个发现的可信程度，确保只报告真正重要的问题，避免误报干扰开发者。

---

## 一、什么是置信度评分？

### 1.1 定义

**置信度评分（Confidence Scoring）** 是对 AI 判断结果可信程度的量化评估，通常使用 0-100 的分数表示。

```
简单理解：
置信度 = AI 对自己判断的确信程度
100 分 = 绝对确定这是真问题
0 分 = 完全不确定，可能是误报
```

### 1.2 为什么需要置信度评分？

**问题背景：**

AI 在分析代码时可能会产生大量"发现"，但并非所有发现都是真正的问题：

```
AI 发现了 50 个"问题"：
- 10 个是真正的 Bug ✅
- 15 个是风格偏好（非问题）❌
- 20 个是误报（理解错误）❌
- 5 个是已存在的旧问题 ❌

如果全部报告给开发者：
→ 信息过载
→ 真正的问题被淹没
→ 开发者失去信任
```

**解决方案：**

使用置信度评分过滤，只报告高置信度的问题：

```
置信度 ≥ 80 的问题：
- 10 个真正的 Bug ✅

结果：
→ 信息精准
→ 开发者专注真正的问题
→ 建立信任
```

### 1.3 在 Claude Code 中的应用

置信度评分主要应用于 `code-reviewer` Agent：

```markdown
## Confidence Scoring

Rate each potential issue on a scale from 0-100:

- **0**: Not confident at all. This is a false positive.
- **25**: Somewhat confident. This might be a real issue.
- **50**: Moderately confident. This is a real issue, but might be a nitpick.
- **75**: Highly confident. This is very likely a real issue.
- **100**: Absolutely certain. Confirmed this is definitely a real issue.

**Only report issues with confidence ≥ 80.**
```

## 二、置信度评分标准详解

### 2.1 评分等级

| 分数 | 等级 | 含义 | 是否报告 | 典型场景 |
|------|------|------|----------|---------|
| **0** | 完全不信 | 误报或已存在问题 | ❌ 不报告 | 理解错误、旧代码问题 |
| **25** | 低置信度 | 可能是问题，也可能是误报 | ❌ 不报告 | 风格问题、规范未明确 |
| **50** | 中等置信度 | 真问题，但不重要 | ❌ 不报告 | 小问题、不常发生 |
| **75** | 高置信度 | 很可能是真问题 | ⚠️ 临界值 | 会影响功能、规范明确 |
| **80+** | 报告阈值 | **只报告这个级别以上** | ✅ 报告 | 重要问题、影响功能 |
| **100** | 绝对确定 | 证据确凿的真问题 | ✅ 报告 | 严重安全漏洞、明显 Bug |

### 2.2 各等级详细说明

#### 0 分：完全不信（Not confident at all）

**定义：** 这是误报，或者不是当前代码的问题。

**场景：**

```javascript
// 场景 1：AI 理解错误
// AI 误以为这是 SQL 注入，但实际上是安全的参数化查询
db.query('SELECT * FROM users WHERE id = ?', [userId]);
// 评分：0 分 - 这是误报

// 场景 2：已存在的旧问题
// 这段代码在修改前就存在，不是本次变更引入的
function oldCode() {
  // 已知的遗留问题
}
// 评分：0 分 - 不是本次审查范围
```

**判断标准：**
- ❌ AI 理解错误
- ❌ 问题不存在
- ❌ 是已存在的旧问题
- ❌ 与当前变更无关

---

#### 25 分：低置信度（Somewhat confident）

**定义：** 可能是问题，但也可能是误报。

**场景：**

```javascript
// 场景 1：风格偏好
// AI 认为应该用 const，但项目没有明确要求
let maxRetries = 3;  // AI 建议用 const
// 评分：25 分 - 风格问题，规范未明确

// 场景 2：可读性建议
// AI 认为变量名不够清晰，但这是主观判断
const d = new Date();  // AI 建议用 currentDate
// 评分：25 分 - 主观判断，非硬性问题

// 场景 3：可能的性能问题
// AI 怀疑有性能问题，但需要实际测试验证
for (let i = 0; i < arr.length; i++) {
  // AI 担心 arr.length 每次都计算
}
// 评分：25 分 - 现代引擎已优化，可能是误报
```

**判断标准：**
- ⚠️ 可能是真问题
- ⚠️ 也可能是误报
- ⚠️ 规范未明确要求
- ⚠️ 主观判断

---

#### 50 分：中等置信度（Moderately confident）

**定义：** 确实是问题，但不重要或不常发生。

**场景：**

```javascript
// 场景 1：小问题
// 缺少类型注解，但不影响运行
function processData(data) {  // AI 建议添加类型
  return data.value;
}
// 评分：50 分 - 是问题，但不重要

// 场景 2：不常发生的边界情况
// 只有在极端情况下才会出问题
function divide(a, b) {
  return a / b;  // AI 担心 b = 0 的情况
}
// 评分：50 分 - 边界情况，不常发生

// 场景 3：代码异味
// 代码可以更好，但不是必须修改
if (condition) {
  // 很多嵌套的 if
}
// 评分：50 分 - 代码异味，但不影响功能
```

**判断标准：**
- ✅ 确实是问题
- ⚠️ 但不重要
- ⚠️ 不常发生
- ⚠️ 不影响核心功能

---

#### 75 分：高置信度（Highly confident）

**定义：** 很可能是真问题，会影响功能或违反规范。

**场景：**

```javascript
// 场景 1：明显的 Bug
// 条件判断错误
if (user.age > 18) {  // 应该是 >= 或 <
  return false;  // 未成年不能访问
}
// 评分：75 分 - 很可能是逻辑错误

// 场景 2：违反项目规范
// CLAUDE.md 明确要求使用 logger
console.log('Debug info');  // 应该用 logger.info()
// 评分：75 分 - 违反明确的项目规范

// 场景 3：潜在的安全问题
// 虽然不是立即的危险，但有风险
const userInput = req.body.data;
eval(userInput);  // 代码注入风险
// 评分：75 分 - 安全风险
```

**判断标准：**
- ✅ 很可能是真问题
- ✅ 会影响功能
- ✅ 违反明确的项目规范
- ✅ 有安全风险

---

#### 100 分：绝对确定（Absolutely certain）

**定义：** 证据确凿，肯定是真问题，会频繁发生。

**场景：**

```javascript
// 场景 1：SQL 注入漏洞
// 明确的安全漏洞
db.query(`SELECT * FROM users WHERE id = ${userId}`);
// 评分：100 分 - 确定的 SQL 注入漏洞

// 场景 2：空指针异常
// 肯定会崩溃
const user = null;
console.log(user.name);  // TypeError: Cannot read property 'name' of null
// 评分：100 分 - 肯定会崩溃

// 场景 3：密码明文存储
// 严重的安全问题
await db.save({ email, password });  // 密码未加密
// 评分：100 分 - 严重安全问题
```

**判断标准：**
- ✅ 证据确凿
- ✅ 肯定是真问题
- ✅ 会频繁发生
- ✅ 严重影响（安全、崩溃）

## 三、80 分报告阈值的设计哲学

### 3.1 为什么是 80 分？

**设计考量：**

```
阈值太低（如 50 分）：
→ 报告太多问题
→ 信息过载
→ 开发者疲劳

阈值太高（如 95 分）：
→ 漏掉一些重要问题
→ 质量保障不足

阈值适中（80 分）：
→ 只报告重要问题
→ 信息精准
→ 开发者信任
```

### 3.2 质量优于数量

**核心理念：**

```
宁可漏报，不可误报

原因：
1. 开发者时间宝贵
2. 误报会降低信任
3. 真问题总会在其他地方被发现
4. 保持高质量输出
```

### 3.3 实际效果对比

**不使用置信度过滤：**

```markdown
## 审查报告

发现 50 个问题：

1. 变量命名不够清晰
2. 可以用 const 代替 let
3. SQL 注入漏洞 ← 真问题被淹没
4. 注释不够详细
5. 函数有点长
...
```

**使用置信度过滤（≥80）：**

```markdown
## 审查报告

发现 3 个高置信度问题：

### Critical
1. 🐛 SQL 注入漏洞
   - 位置：src/auth.ts:45
   - 置信度：100/100
   - 修复：使用参数化查询

### Warning
2. ⚠️ 密码未加密存储
   - 位置：src/user.ts:78
   - 置信度：95/100
   - 修复：使用 bcrypt 加密

3. ⚠️ 缺少错误处理
   - 位置：src/api.ts:123
   - 置信度：85/100
   - 修复：添加 try-catch
```

## 四、如何应用置信度评分

### 4.1 在 Agent 中配置

**code-reviewer 的配置示例：**

```markdown
---
name: code-reviewer
description: Reviews code for bugs, security vulnerabilities, and code quality issues
model: inherit
color: red
---

You are an expert code reviewer.

## Confidence Scoring

Rate each potential issue on a scale from 0-100:

- **0**: Not confident at all. This is a false positive.
- **25**: Somewhat confident. This might be a real issue.
- **50**: Moderately confident. This is a real issue, but might be a nitpick.
- **75**: Highly confident. This is very likely a real issue.
- **100**: Absolutely certain. Confirmed this is definitely a real issue.

**Only report issues with confidence ≥ 80.**

## Output Format

For each high-confidence issue, provide:
- Clear description with confidence score
- File path and line number
- Specific project guideline reference or bug explanation
- Concrete fix suggestion
```

### 4.2 在 Hook 中应用

**示例：安全检查 Hook**

```json
{
  "event": "PreToolUse",
  "matcher": "Write",
  "type": "prompt",
  "prompt": "Before writing code, check for security issues:\n\n1. SQL injection\n2. XSS vulnerabilities\n3. Hardcoded secrets\n\nFor each issue found, rate confidence (0-100).\nOnly block the operation if confidence ≥ 80.\n\nIf blocking, explain the security risk clearly."
}
```

### 4.3 在 Skill 中应用

**示例：代码审查 Skill**

```markdown
---
name: code-review-skill
description: This skill should be used when reviewing code for quality and security.
---

When reviewing code:

1. Identify potential issues
2. Rate each issue with confidence score (0-100)
3. Only report issues with confidence ≥ 80
4. Provide clear fix suggestions

Confidence levels:
- 0-25: Likely false positive, don't report
- 50-75: Minor issue, don't report unless critical
- 80-100: Real issue, report with details
```

## 五、置信度评分实战案例

### 案例 1：SQL 注入检测

```javascript
// 代码
db.query(`SELECT * FROM users WHERE email = '${email}'`);

// AI 分析
发现：字符串拼接 SQL 查询
风险评估：SQL 注入
证据：直接将用户输入拼接到 SQL
频率：每次调用都会发生
严重性：可获取整个数据库

// 置信度评分：100/100
// 理由：证据确凿，严重安全漏洞，每次都会发生
```

### 案例 2：空指针异常

```javascript
// 代码
function getUserName(user) {
  return user.profile.name;
}

// AI 分析
发现：未检查 user 和 profile 是否存在
风险评估：TypeError
证据：如果 user 为 null 或 user.profile 为 undefined
频率：取决于调用方，可能发生
严重性：导致程序崩溃

// 置信度评分：85/100
// 理由：很可能是问题，但需要看调用方是否保证 user 非空
```

### 案例 3：代码风格

```javascript
// 代码
let maxCount = 10;

// AI 分析
发现：使用了 let 但值从未改变
建议：可以改为 const
证据：代码中没有对 maxCount 重新赋值
规范：项目规范未明确要求

// 置信度评分：25/100
// 理由：风格建议，规范未明确，不是真正的问题
// 结果：不报告
```

### 案例 4：性能问题

```javascript
// 代码
for (let i = 0; i < largeArray.length; i++) {
  for (let j = 0; j < largeArray.length; j++) {
    // 嵌套循环
  }
}

// AI 分析
发现：O(n²) 复杂度
风险评估：性能问题
证据：双重循环
频率：只有在大数组时才明显
严重性：性能下降，但不会崩溃

// 置信度评分：60/100
// 理由：是问题，但取决于数据规模
// 结果：不报告（低于 80）
```

## 六、置信度评分的局限性

### 6.1 可能漏报

**问题：** 某些真正的问题可能置信度低于 80

**解决方案：**
- 定期审查低置信度问题
- 根据实际情况调整阈值
- 结合其他检测手段

### 6.2 主观性

**问题：** 置信度评分本身有一定主观性

**解决方案：**
- 提供明确的评分标准
- 多 Agent 交叉验证
- 人工审核关键问题

### 6.3 上下文依赖

**问题：** 同一问题在不同上下文中置信度不同

**示例：**

```javascript
// 场景 1：内部工具
eval(userInput);  // 置信度：75（可能是有意为之）

// 场景 2：面向公众的 API
eval(userInput);  // 置信度：100（肯定是安全问题）
```

**解决方案：**
- 考虑项目背景
- 参考 CLAUDE.md 中的上下文
- 区分不同使用场景

## 七、最佳实践

### 7.1 设置合适的阈值

| 场景 | 建议阈值 | 理由 |
|------|---------|------|
| **安全审查** | 70-80 | 安全问题宁可多报 |
| **代码质量** | 80-85 | 平衡质量和效率 |
| **风格检查** | 90-95 | 风格问题少报 |

### 7.2 结合项目规范

```markdown
项目规范（CLAUDE.md）明确要求的内容：
→ 违反时置信度更高（+10 到 +20）

项目规范未明确的内容：
→ 置信度较低
```

### 7.3 多维度评估

```
置信度 = 基础置信度 + 调整因子

调整因子：
+20：项目规范明确要求
+10：有安全风险
+10：会导致崩溃
-10：边界情况
-20：主观判断
```
