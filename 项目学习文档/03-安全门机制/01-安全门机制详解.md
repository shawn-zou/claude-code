# 安全门机制详解

## 一、什么是安全门机制

### 1.1 基本概念

**安全门（Security Gate）**是一种基于 Hook 系统实现的安全防护机制。想象一下你家的防盗门：
- 有人要进门 → 安全门检查 → 是家人就开门，是陌生人就报警

在 Claude Code 中，安全门机制也是这样工作的：
- Claude 要执行操作 → 安全门检查 → 安全就允许，危险就警告

### 1.2 安全门与 Hook 的关系

**Hook 系统是基础设施**，就像房子的电路系统。
**安全门机制是应用**，就像安装在电路系统上的防盗报警器。

```
Hook 系统 = 基础能力（可以触发任何事件）
    ↓
安全门机制 = 具体应用（专门用于安全检查的 Hook）
```

**简单说：** 安全门机制 = Hook 系统在安全领域的具体应用

## 二、为什么需要安全门机制

### 2.1 真实场景中的安全问题

**场景 1：意外的破坏性操作**
```
用户：帮我清理一下项目中的临时文件
Claude: 好的，我删除所有 .tmp 文件

风险：如果 Claude 不小心删除了重要的 .tmp 配置文件呢？
```

**有了安全门：**
```
用户：帮我清理一下项目中的临时文件
Claude: 好的，我准备删除这些文件...
安全门：⚠️ 检测到删除操作！这些文件中包含 config.tmp（重要配置），确定要删除吗？
用户：哦！谢谢提醒，保留那个文件。
```

**场景 2：代码中的安全漏洞**
```
用户：帮我写一个用户登录功能
Claude: 好的，这是代码...（包含了 SQL 注入风险）

风险：攻击者可以利用 SQL 注入获取所有用户数据
```

**有了安全门：**
```
用户：帮我写一个用户登录功能
Claude: 好的，这是代码...
安全门：⚠️ 检测到 SQL 注入风险！这段代码直接拼接用户输入，建议使用参数化查询。
Claude: 谢谢提醒，我修改为使用参数化查询。
```

### 2.2 安全门的核心价值

1. **预防意外**：阻止无意的破坏性操作
2. **提前预警**：在问题发生前发出警报
3. **教育引导**：帮助用户和 Claude 学习最佳实践
4. **强制执行**：确保某些规则必须遵守

## 三、安全门的实现原理

### 3.1 四层防护架构

Claude Code 的安全门机制采用四层防护，就像城堡的多道防线：

```
第一层：会话开始时的安全提醒
         ↓
第二层：工具使用前的安全检查
         ↓
第三层：代码写入后的安全验证
         ↓
第四层：任务完成前的最终审核
```

#### 第一层：SessionStart Hook - 安全意识提醒

**作用：** 在每个会话开始时提醒注意安全。

**实现方式：**
```json
{
  "hooks": {
    "SessionStart": [
      {
        "type": "command",
        "command": "echo '安全提醒：本会话中请注意代码安全'"
      }
    ]
  }
}
```

**效果：**
```
[系统] 安全提醒：
- 检查代码中的安全漏洞
- 避免硬编码密钥
- 使用参数化查询防止 SQL 注入
```

#### 第二层：PreToolUse Hook - 操作前检查

**作用：** 在危险操作（删除、写入、执行命令）前进行检查。

**实现示例：**
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "type": "prompt",
        "prompt": "检查这个操作是否有安全风险：$TOOL_INPUT\n特别关注：\n1. 删除文件操作\n2. 覆盖重要文件\n3. 执行危险命令（rm, sudo 等）",
        "timeout": 30
      }
    ]
  }
}
```

**工作流程：**
```
Claude 准备删除文件
    ↓
安全门触发（PreToolUse）
    ↓
AI 分析："检测到删除操作，目标文件：config.json"
    ↓
AI 判断："这是配置文件，删除可能导致系统故障"
    ↓
安全门：⚠️ 警告！删除 config.json 可能影响系统运行
    ↓
用户决定：取消或确认
```

#### 第三层：PostToolUse Hook - 操作后验证

**作用：** 在代码写入后检查是否有安全问题。

**实现示例：**
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "type": "prompt",
        "prompt": "检查刚刚写入的代码是否有安全漏洞：$TOOL_RESULT\n检查项：\n1. SQL 注入\n2. XSS 攻击\n3. 硬编码的密钥\n4. 命令注入",
        "timeout": 30
      }
    ]
  }
}
```

**工作流程：**
```
Claude 写完代码
    ↓
安全门触发（PostToolUse）
    ↓
AI 检查代码中的安全问题
    ↓
发现："第 15 行有 SQL 注入风险"
    ↓
安全门：⚠️ 发现安全漏洞！建议修复。
```

#### 第四层：Stop Hook - 最终审核

**作用：** 在 Claude 完成任务前做最后的安全检查。

**实现示例：**
```json
{
  "hooks": {
    "Stop": [
      {
        "type": "prompt",
        "prompt": "本次会话的所有修改是否有安全风险？检查：\n1. 是否引入了新漏洞\n2. 是否暴露了敏感信息\n3. 是否破坏了现有安全措施",
        "timeout": 30
      }
    ]
  }
}
```

### 4.5 第五层：PostToolUse Hook - 操作后验证（新增）

**作用：** 在工具执行完成后立即检查结果，发现问题并给出反馈。

**与 PreToolUse 的区别：**
- **PreToolUse**：操作前预防（事前）
- **PostToolUse**：操作后验证（事中）

**工作流程：**
```
Claude 完成代码写入
    ↓
PostToolUse Hook 触发
    ↓
AI 分析写入的代码
    ↓
发现潜在问题 → 立即提醒
    ↓
Claude 可以立即修复
```

**实现示例：**
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "prompt",
            "prompt": "分析刚刚写入的代码：$TOOL_RESULT\n\n检查项：\n1. 是否有语法错误\n2. 是否引入了安全漏洞\n3. 是否破坏了现有功能\n4. 是否需要更新测试\n\n如有问题，立即指出并提供修复建议。",
            "timeout": 30
          }
        ]
      }
    ]
  }
}
```

**实战效果：**
```
Claude: 好的，我已经写入了用户登录函数

// 写入的代码
function login(username, password) {
  const query = "SELECT * FROM users WHERE username='" + username + "' AND password='" + password + "'";
  return db.query(query);
}

安全门（PostToolUse）：⚠️ 发现严重安全问题！

问题分析：
1. ❌ SQL 注入漏洞 - 直接拼接用户输入到 SQL 语句
   攻击者可以输入：admin' -- 绕过密码验证

2. ❌ 明文密码存储 - 密码应该哈希后存储
   建议使用 bcrypt 或 argon2

修复建议：
```javascript
// ✅ 使用参数化查询
const bcrypt = require('bcrypt');

async function login(username, password) {
  // 使用参数化查询防止 SQL 注入
  const user = await db.query(
    'SELECT * FROM users WHERE username = ?',
    [username]
  );
  
  if (!user) return null;
  
  // 验证哈希密码
  const valid = await bcrypt.compare(password, user.password);
  return valid ? user : null;
}
```

Claude: 谢谢提醒！我立即修复这个问题。
```

## 六、实战案例：security-guidance 插件

### 6.1 插件介绍

**位置：** `plugins/security-guidance/`

**功能：** 在执行可能不安全的操作前警告用户。

**作者：** David Dworken (dworken@anthropic.com)

### 6.2 配置文件详解

**插件配置：** `.claude-plugin/plugin.json`
```json
{
  "name": "security-guidance",
  "version": "1.0.0",
  "description": "Security reminder hook that warns about potential security issues when editing files, including command injection, XSS, and unsafe code patterns",
  "author": {
    "name": "David Dworken",
    "email": "dworken@anthropic.com"
  }
}
```

**Hook 配置：** `hooks/hooks.json`
```json
{
  "description": "Security reminder hook that warns about potential security issues when editing files",
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/security_reminder_hook.py"
          }
        ],
        "matcher": "Edit|Write|MultiEdit"
      }
    ]
  }
}
```

**配置说明：**
- **matcher**: `"Edit|Write|MultiEdit"` 使用正则表达式匹配工具名，只在编辑/写入文件时触发
- **type: command**: 实际实现使用的是 Command Hook（Python 脚本），而非 Prompt Hook
- **优势**: 基于字符串匹配，速度快、准确性高、无需等待 AI 响应

**核心实现逻辑：** Python 脚本 `security_reminder_hook.py` 包含以下关键功能：

1. **安全模式检测**：预定义的安全规则列表
2. **路径检查**：针对特定文件路径的检查（如 GitHub Actions 工作流）
3. **内容检查**：检测代码中的危险模式（如 eval、exec 等）
4. **会话状态管理**：避免在同一会话中重复显示相同警告
5. **智能退出码**：
   - `exit(0)`: 允许执行
   - `exit(2)`: 阻塞执行并显示警告

### 6.3 九大安全检测模式详解

security-guidance 实现了 9 种常见的安全漏洞检测：

#### 模式 1：GitHub Actions 工作流注入检测

**检测对象：** `.github/workflows/*.yml` 文件

**风险说明：** GitHub Actions 工作流文件中直接使用未过滤的用户输入可能导致命令注入。

**危险示例：**
```yaml
# ❌ 危险：直接使用用户输入
run: echo "${{ github.event.issue.title }}"
```

**安全做法：**
```yaml
# ✅ 安全：使用环境变量间接引用
env:
  TITLE: ${{ github.event.issue.title }}
run: echo "$TITLE"
```

**常见危险输入源：**
- `github.event.issue.title` / `github.event.issue.body`
- `github.event.pull_request.title` / `body`
- `github.event.comment.body`
- `github.event.commits.*.message`
- `github.head_ref`

#### 模式 2：child_process.exec 命令注入

**检测字符串：** `child_process.exec`, `exec(`, `execSync(`

**风险说明：** Node.js 中使用 `exec()` 执行 shell 命令时，如果参数包含用户输入，可能导致命令注入。

**危险示例：**
```javascript
// ❌ 危险：拼接用户输入
exec(`git clone ${userInput}`);
```

**安全做法：**
```javascript
// ✅ 安全：使用 execFileNoThrow 工具
import { execFileNoThrow } from '../utils/execFileNoThrow.js';
await execFileNoThrow('git', ['clone', userInput]);
```

#### 模式 3：new Function 代码注入

**检测字符串：** `new Function`

**风险说明：** 使用 `new Function()` 动态执行代码字符串，如果字符串包含用户输入，可能导致任意代码执行。

**建议：** 除非确实需要执行动态代码，否则使用其他替代方案。

#### 模式 4：eval 注入

**检测字符串：** `eval(`

**风险说明：** `eval()` 直接执行字符串作为 JavaScript 代码，是严重的安全风险。

**示例：**
```javascript
// ❌ 极度危险
const userData = JSON.parse(userInput);  // ✅ 正确
const userData = eval('(' + userInput + ')');  // ❌ 错误
```

#### 模式 5：React dangerouslySetInnerHTML

**检测字符串：** `dangerouslySetInnerHTML`

**风险说明：** React 中直接渲染 HTML 可能导致 XSS 攻击，如果内容来自用户输入。

**安全做法：**
```javascript
// ✅ 使用 DOMPurify 等库进行消毒
import DOMPurify from 'dompurify';
const cleanHTML = DOMPurify.sanitize(dirtyHTML);
```

#### 模式 6：document.write XSS

**检测字符串：** `document.write`

**风险说明：** `document.write()` 可能引入 XSS 漏洞，且有性能问题。

**替代方案：**
```javascript
// ✅ 使用 DOM 操作方法
const element = document.createElement('div');
element.textContent = safeText;
document.body.appendChild(element);
```

#### 模式 7：innerHTML 赋值 XSS

**检测字符串：** `.innerHTML =`, `.innerHTML=`

**风险说明：** 直接设置 innerHTML 属性可能引入恶意脚本。

**安全做法：**
```javascript
// ✅ 使用 textContent（纯文本）
element.textContent = userInput;

// ✅ 或使用 DOMPurify 消毒 HTML
import DOMPurify from 'dompurify';
element.innerHTML = DOMPurify.sanitize(userHTML);
```

#### 模式 8：pickle 反序列化

**检测字符串：** `pickle`

**风险说明：** Python 的 pickle 模块反序列化不可信数据可能导致任意代码执行。

**示例：**
```python
# ❌ 危险：反序列化不可信数据
import pickle
data = pickle.loads(untrusted_data)

# ✅ 安全：使用 JSON
import json
data = json.loads(safe_data)
```

#### 模式 9：os.system 命令注入

**检测字符串：** `os.system`, `from os import system`

**风险说明：** Python 中使用 `os.system()` 执行 shell 命令时，参数必须是静态的，不能包含用户输入。

**安全做法：**
```python
# ❌ 危险
os.system(f"ls {user_input}")

# ✅ 安全：使用 subprocess 和参数列表
import subprocess
subprocess.run(['ls', user_input])
```

### 6.4 实现细节剖析

#### 核心代码结构

```python
#!/usr/bin/env python3
"""Security Reminder Hook for Claude Code"""

import json
import os
import sys

# 安全模式配置
SECURITY_PATTERNS = [
    {
        "ruleName": "github_actions_workflow",
        "path_check": lambda path: ".github/workflows/" in path,
        "reminder": "You are editing a GitHub Actions workflow..."
    },
    {
        "ruleName": "child_process_exec",
        "substrings": ["child_process.exec", "exec(", "execSync("],
        "reminder": "⚠️ Security Warning: Using child_process.exec()..."
    },
    # ... 其他模式
]

def check_patterns(file_path, content):
    """检查文件路径和内容是否匹配安全模式"""
    normalized_path = file_path.lstrip("/")
    
    for pattern in SECURITY_PATTERNS:
        # 检查路径模式
        if "path_check" in pattern and pattern["path_check"](normalized_path):
            return pattern["ruleName"], pattern["reminder"]
        
        # 检查内容模式
        if "substrings" in pattern and content:
            for substring in pattern["substrings"]:
                if substring in content:
                    return pattern["ruleName"], pattern["reminder"]
    
    return None, None

def main():
    # 读取标准输入
    raw_input = sys.stdin.read()
    input_data = json.loads(raw_input)
    
    # 提取信息
    session_id = input_data.get("session_id", "default")
    tool_name = input_data.get("tool_name", "")
    tool_input = input_data.get("tool_input", {})
    file_path = tool_input.get("file_path", "")
    
    # 提取内容
    content = extract_content_from_input(tool_name, tool_input)
    
    # 检查安全模式
    rule_name, reminder = check_patterns(file_path, content)
    
    if rule_name and reminder:
        # 创建唯一警告键
        warning_key = f"{file_path}-{rule_name}"
        
        # 加载已显示的警告（会话级别）
        shown_warnings = load_state(session_id)
        
        # 避免重复警告
        if warning_key not in shown_warnings:
            shown_warnings.add(warning_key)
            save_state(session_id, shown_warnings)
            
            # 输出警告并阻塞
            print(reminder, file=sys.stderr)
            sys.exit(2)  # 阻塞执行
    
    sys.exit(0)  # 允许执行

if __name__ == "__main__":
    main()
```

#### 会话状态管理机制

为了避免在同一会话中重复显示相同的警告，security-guidance 使用了会话级别的状态管理：

**状态文件位置：** `~/.claude/security_warnings_state_{session_id}.json`

**状态管理流程：**
```python
def get_state_file(session_id):
    """获取会话特定的状态文件路径"""
    return os.path.expanduser(f"~/.claude/security_warnings_state_{session_id}.json")

def load_state(session_id):
    """加载已显示的警告集合"""
    state_file = get_state_file(session_id)
    if os.path.exists(state_file):
        with open(state_file, "r") as f:
            return set(json.load(f))
    return set()

def save_state(session_id, shown_warnings):
    """保存已显示的警告集合"""
    state_file = get_state_file(session_id)
    with open(state_file, "w") as f:
        json.dump(list(shown_warnings), f)
```

**自动清理机制：**
- 每次运行有 10% 的概率清理超过 30 天的旧状态文件
- 保持系统整洁，避免状态文件堆积

## 六、Hook API 技术参考

本节详细介绍 Hook 系统的底层技术细节，包括事件类型、输入输出格式、退出码等。

### 6.1 完整的事件类型列表

除了前面介绍的 4 种基本事件类型，Hook 系统还支持以下事件：

| 事件类型 | 触发时机 | 典型用途 | 支持 Prompt Hook |
|----------|----------|----------|------------------|
| **PreToolUse** | 工具使用前 | 安全检查、权限验证 | ✅ |
| **PostToolUse** | 工具使用后 | 结果分析、日志记录 | ✅ |
| **Stop** | 主代理停止前 | 任务完整性检查 | ✅ |
| **SubagentStop** | 子代理停止前 | 子任务完成度检查 | ✅ |
| **UserPromptSubmit** | 用户提交提示时 | 提示词分析、上下文增强 | ✅ |
| **SessionStart** | 会话开始时 | 加载配置、环境设置 | ❌ |
| **SessionEnd** | 会话结束时 | 清理、归档、统计 | ❌ |
| **PreCompact** | 上下文压缩前 | 保留关键信息 | ❌ |
| **Notification** | 发送通知时 | 通知日志、外部集成 | ❌ |

**说明：**
- ✅ 表示支持 Prompt Hook（基于 AI 的智能判断）
- ❌ 表示通常使用 Command Hook（确定性脚本）

### 6.2 Hook 输入格式详解

所有 Hook 都通过标准输入（stdin）接收 JSON 数据：

**通用字段：**
```json
{
  "session_id": "abc123",              // 会话唯一标识
  "transcript_path": "/path/to/transcript.txt",  // 对话记录文件路径
  "cwd": "/current/working/dir",       // 当前工作目录
  "permission_mode": "ask|allow",      // 权限模式
  "hook_event_name": "PreToolUse"      // Hook 事件名称
}
```

**事件特定字段：**

**PreToolUse / PostToolUse:**
```json
{
  // ... 通用字段
  "tool_name": "Write",                // 工具名称
  "tool_input": {                      // 工具输入参数
    "file_path": "/path/to/file",
    "content": "file content"
  },
  "tool_result": "..."                 // 工具执行结果（仅 PostToolUse）
}
```

**UserPromptSubmit:**
```json
{
  // ... 通用字段
  "user_prompt": "用户提交的原始提示词"
}
```

**Stop / SubagentStop:**
```json
{
  // ... 通用字段
  "reason": "Task appears complete"     // 停止原因
}
```

### 6.3 Hook 输出格式详解

不同类型的 Hook 有不同的输出格式要求：

#### PreToolUse 输出格式

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow|deny|ask",  // 权限决策
    "updatedInput": {                        // 修改后的输入（可选）
      "field": "modified_value"
    }
  },

}
```

**决策说明：**
- `allow`: 允许工具执行
- `deny`: 阻止工具执行
- `ask`: 询问用户决定

#### Stop / SubagentStop 输出格式

```json
{
  "decision": "approve|block",           // 是否允许停止

```

#### 通用输出格式（所有 Hook）

```json
{

### 6.4 退出码的含义

Command Hook 通过退出码传达决策：

| 退出码 | 含义 | 效果 |
|--------|------|------|
| **0** | 成功 | 允许执行，stdout 显示在记录中 |
| **2** | 阻塞性错误 | 阻止执行，stderr 反馈给 Claude |
| **其他值** | 非阻塞错误 | 记录错误但不阻止执行 |

**示例：**
```bash
#!/bin/bash

# 允许执行
exit 0

# 阻止执行（显示错误）
echo "检测到安全问题！" >&2
exit 2

# 警告但不阻止
echo "建议改进..." >&2
exit 1
```

### 6.5 Matcher 语法详解

Matcher 用于精确控制 Hook 在哪些工具上触发，支持正则表达式：

**基本语法：**
```json

}
```

**常用 Matcher 模式：**

| Matcher 模式 | 匹配的工具 | 用途 |
|------------|-----------|------|
| `"*"` | 所有工具 | 全局 Hook |
| `"Write"` | 仅 Write 工具 | 文件写入检查 |
| `"Write|Edit"` | Write 或 Edit | 文件修改检查 |
| `"Bash"` | Bash 工具 | 命令执行检查 |
| `"mcp__.*__delete.*"` | MCP 删除操作 | MCP 工具检查 |

**MCP 工具 Matcher 示例：**
```json
{
  "matcher": "mcp__filesystem__delete"  // 匹配特定 MCP 工具的删除操作
}
```

## 七、高级安全技术

### 7.1 多阶段验证（Multi-Stage Validation）

结合 Command Hook 和 Prompt Hook 实现分层验证：

**架构设计：**
```
快速检查（Command Hook, 1-2 秒）
    ↓ 通过
深度检查（Prompt Hook, 10-20 秒）
    ↓ 通过
执行操作
```

**配置示例：**
```json
{
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        {
          "type": "command",
          "command": "bash ${CLAUDE_PLUGIN_ROOT}/scripts/quick-check.sh",
          "timeout": 5
        },
        {
          "type": "prompt",
          "prompt": "深度分析 bash 命令的安全性：$TOOL_INPUT",
          "timeout": 15
        }
      ]
    }
  ]
}
```

**快速检查脚本示例（quick-check.sh）：**
```bash
#!/bin/bash
input=$(cat)

  exit 0
fi

# 复杂情况交给 Prompt Hook 处理

```

**优势：**
- ✅ 快速路径：常见安全命令几乎无延迟
- ✅ 深度分析：复杂命令获得智能分析
- ✅ 性能优化：减少不必要的 AI 调用

### 7.3 状态跟踪与审计

使用临时文件或数据库在 Hook 之间共享状态：

#### PostToolUse 跟踪事件

```bash
#!/bin/bash

  if [[ "$command" == *"test"* ]]; then
    count=$(cat /tmp/test-count-$$ 2>/dev/null || echo "0")
    echo $((count + 1)) > /tmp/test-count-$$
  fi
fi

exit 0
```

#### Stop 基于历史状态验证

```bash
#!/bin/bash
# Stop Hook：基于跟踪状态验证

  exit 2

exit 0
```

## 六、Hook API 技术参考

本节详细介绍 Hook 系统的底层技术细节，包括事件类型、输入输出格式、退出码等。

### 6.1 完整的事件类型列表

除了前面介绍的 4 种基本事件类型，Hook 系统还支持以下事件：

| 事件类型 | 触发时机 | 典型用途 | 支持 Prompt Hook |
|----------|----------|----------|------------------|
| **PreToolUse** | 工具使用前 | 安全检查、权限验证 | ✅ |
| **PostToolUse** | 工具使用后 | 结果分析、日志记录 | ✅ |
| **Stop** | 主代理停止前 | 任务完整性检查 | ✅ |
| **SubagentStop** | 子代理停止前 | 子任务完成度检查 | ✅ |
| **UserPromptSubmit** | 用户提交提示时 | 提示词分析、上下文增强 | ✅ |
| **SessionStart** | 会话开始时 | 加载配置、环境设置 | ❌ |
| **SessionEnd** | 会话结束时 | 清理、归档、统计 | ❌ |
| **PreCompact** | 上下文压缩前 | 保留关键信息 | ❌ |
| **Notification** | 发送通知时 | 通知日志、外部集成 | ❌ |

**说明：**
- ✅ 表示支持 Prompt Hook（基于 AI 的智能判断）
- ❌ 表示通常使用 Command Hook（确定性脚本）

### 6.2 Hook 输入格式详解

所有 Hook 都通过标准输入（stdin）接收 JSON 数据：

**通用字段：**
```json
{
  "session_id": "abc123",              // 会话唯一标识
  "transcript_path": "/path/to/transcript.txt",  // 对话记录文件路径
  "cwd": "/current/working/dir",       // 当前工作目录
  "permission_mode": "ask|allow",      // 权限模式
  "hook_event_name": "PreToolUse"      // Hook 事件名称
}
```

**事件特定字段：**

**PreToolUse / PostToolUse:**
```json
{
  // ... 通用字段
  "tool_name": "Write",                // 工具名称
  "tool_input": {                      // 工具输入参数
    "file_path": "/path/to/file",
    "content": "file content"
  },
  "tool_result": "..."                 // 工具执行结果（仅 PostToolUse）
}
```

**UserPromptSubmit:**
```json
{
  // ... 通用字段
  "user_prompt": "用户提交的原始提示词"
}
```

**Stop / SubagentStop:**
```json
{
  // ... 通用字段
  "reason": "Task appears complete"     // 停止原因
}
```

### 6.3 Hook 输出格式详解

不同类型的 Hook 有不同的输出格式要求：

#### PreToolUse 输出格式

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "allow|deny|ask",  // 权限决策
    "updatedInput": {                        // 修改后的输入（可选）
      "field": "modified_value"
    }
  },
  "systemMessage": "解释说明，将显示给 Claude"  // 可选
}
```

**决策说明：**
- `allow`: 允许工具执行
- `deny`: 阻止工具执行
- `ask`: 询问用户决定

#### Stop / SubagentStop 输出格式

```json
{
  "decision": "approve|block",           // 是否允许停止
  "reason": "详细说明为什么阻止",         // 阻止原因
  "systemMessage": "额外的上下文信息"     // 可选
}
```

#### 通用输出格式（所有 Hook）

```json
{
  "continue": true|false,                // 是否继续处理
  "suppressOutput": true|false,          // 是否隐藏输出
  "systemMessage": "消息内容"            // 显示给 Claude 的消息
}
```

### 6.4 退出码的含义

Command Hook 通过退出码传达决策：

| 退出码 | 含义 | 效果 |
|--------|------|------|
| **0** | 成功 | 允许执行，stdout 显示在记录中 |
| **2** | 阻塞性错误 | 阻止执行，stderr 反馈给 Claude |
| **其他值** | 非阻塞错误 | 记录错误但不阻止执行 |

**示例：**
```bash
#!/bin/bash

# 允许执行
exit 0

# 阻止执行（显示错误）
echo "检测到安全问题！" >&2
exit 2

# 警告但不阻止
echo "建议改进..." >&2
exit 1
```

### 6.5 Matcher 语法详解

Matcher 用于精确控制 Hook 在哪些工具上触发，支持正则表达式：

**基本语法：**
```json
{
  "matcher": "Write|Edit|MultiEdit"    // 匹配多个工具
}
```

**常用 Matcher 模式：**

| Matcher 模式 | 匹配的工具 | 用途 |
|------------|-----------|------|
| `"*"` | 所有工具 | 全局 Hook |
| `"Write"` | 仅 Write 工具 | 文件写入检查 |
| `"Write|Edit"` | Write 或 Edit | 文件修改检查 |
| `"Bash"` | Bash 工具 | 命令执行检查 |
| `"mcp__.*__delete.*"` | MCP 删除操作 | MCP 工具检查 |

**MCP 工具 Matcher 示例：**
```json
{
  "matcher": "mcp__filesystem__delete"  // 匹配特定 MCP 工具的删除操作
}
```

### 6.6 环境变量参考

Hook 脚本可以访问以下特殊环境变量：

| 环境变量 | 含义 | 示例用法 |
|---------|------|----------|
| `${CLAUDE_PLUGIN_ROOT}` | 插件根目录 | `bash ${CLAUDE_PLUGIN_ROOT}/scripts/check.sh` |
| `${CLAUDE_PROJECT_DIR}` | 项目根目录 | `cd "$CLAUDE_PROJECT_DIR"` |
| `${CLAUDE_ENV_FILE}` | 环境变量文件 | `echo "export KEY=value" >> "$CLAUDE_ENV_FILE"` |
| `${TRANSCRIPT_PATH}` | 对话记录路径 | `cat "$TRANSCRIPT_PATH" | grep ...` |
| `${TOOL_INPUT}` | 工具输入（Prompt Hook） | 在 prompt 中引用 |
| `${TOOL_RESULT}` | 工具结果（PostToolUse） | 在 prompt 中引用 |
| `${USER_PROMPT}` | 用户提示词 | 在 UserPromptSubmit 中使用 |

**SessionStart 专用：持久化环境变量**

```bash
#!/bin/bash
# SessionStart Hook 中可以持久化环境变量

这些环境变量将在整个会话期间保持有效。

## 七、高级安全技术

### 7.1 多阶段验证（Multi-Stage Validation）

结合 Command Hook 和 Prompt Hook 实现分层验证：

**架构设计：**
```
快速检查（Command Hook, 1-2 秒）
    ↓ 通过
深度检查（Prompt Hook, 10-20 秒）
    ↓ 通过
执行操作
```

**配置示例：**
```json
{
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        {
          "type": "command",
          "command": "bash ${CLAUDE_PLUGIN_ROOT}/scripts/quick-check.sh",
          "timeout": 5
        },
        {
          "type": "prompt",
          "prompt": "深度分析 bash 命令的安全性：$TOOL_INPUT",
          "timeout": 15
        }
      ]
    }
  ]
}
```

**快速检查脚本示例（quick-check.sh）：**
```bash
#!/bin/bash
input=$(cat)
command=$(echo "$input" | jq -r '.tool_input.command')

# 立即批准明显安全的命令
if [[ "$command" =~ ^(ls|pwd|echo|date|whoami)$ ]]; then
  exit 0
fi

# 复杂情况交给 Prompt Hook 处理
exit 0
```

**优势：**
- ✅ 快速路径：常见安全命令几乎无延迟
- ✅ 深度分析：复杂命令获得智能分析
- ✅ 性能优化：减少不必要的 AI 调用

### 7.2 条件执行策略

## 八、安全门的类型

### 6.1 按检查时机分类

| 类型 | 时机 | 优点 | 缺点 |
|------|------|------|------|
| **事前预防型** | 操作前检查 | 防止问题发生 | 可能有误报 |
| **事中监控型** | 操作中检查 | 实时反馈 | 无法完全阻止 |
| **事后审计型** | 操作后检查 | 全面深入 | 损失已造成 |

**推荐策略：** 结合使用，事前预防为主，事中事后为辅。

### 6.2 按检查内容分类

#### 代码安全类

**检查内容：**
- SQL 注入
- XSS 攻击
- 命令注入
- 缓冲区溢出
- 认证授权问题

**实现示例：**
```json
{
  "type": "prompt",

#### 数据安全类

**检查内容：**

## 九、安全门的效果评估

### 7.1 评估指标

**准确率指标：**
- **检出率**：发现真正安全问题的能力
  - 公式：检出的问题数 / 实际存在的问题数
  - 目标：> 90%
  
- **误报率**：错误报告问题的比例
  - 公式：误报数 / 总报告数
  - 目标：< 10%

**效率指标：**
- **响应时间**：从触发到输出结果的时间
  - Prompt Hook: 理想 < 10 秒
  - Command Hook: 理想 < 2 秒
  
- **吞吐量**：单位时间能检查的操作数
  - 目标：不影响正常工作流

### 7.2 如何优化效果

**提高检出率：**
1. 完善检查清单（覆盖更多安全问题）
2. 使用多个 Hook 从不同角度检查
3. 定期更新安全知识库

**降低误报率：**
1. 细化检查规则（更具体的判断条件）
2. 添加白名单（信任的操作类型）
3. 使用 AI 智能判断而非简单匹配

**提升性能：**
1. 分层检查（快速初筛 + 深度精查）
2. 并行处理（多个 Hook 同时检查）
3. 缓存结果（相同操作不重复检查）

## 十、常见问题与解决方案

### Q1: 安全门总是误报怎么办？

**问题表现：**
```
安全门频繁报警，但大部分都不是真正的问题
→ 用户体验差，逐渐忽视警报
```

**解决方案：**

**方案 1：细化规则**
```json
// ❌ 模糊的规则
"prompt": "检查是否有安全问题"

// ✅ 具体的规则
"prompt": "检查以下具体问题：\n1. SQL 语句中包含用户输入的变量且未使用参数化查询\n2. HTML 输出中包含未转义的用户输入\n3. ..."
```

**方案 2：添加上下文理解**
```json
"prompt": "结合代码上下文判断：\n- 如果是测试代码，放宽标准\n- 如果是生产代码，严格检查\n- 如果是原型开发，适度容忍"
```

**方案 3：使用置信度评分**
```json
"prompt": "对每个发现的问题给出置信度评分（0-100）：\n- 90-100: 非常确定是真问题\n- 70-89: 可能是真问题\n- 50-69: 不确定\n只报告置信度 > 80 的问题"
```

### Q2: 安全门影响性能怎么办？

**问题表现：**
```
每次操作都要等很久才能完成
→ 工作效率低下
```

**解决方案：**

**方案 1：分层过滤**
```
快速检查（Command Hook, 1-2 秒）
    ↓ 通过
深度检查（Prompt Hook, 10-20 秒）
    ↓ 通过
执行操作
```

**方案 2：按需启用**
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "type": "command",
        "command": "test \"$DANGEROUS_OPERATION\" = \"true\" && echo '需要检查'",
        "timeout": 5
      }
    ]
  }
}
```

只在真正危险的操作时才启用深度检查。

**方案 3：异步检查**
```
发起操作 → 立即执行 → 后台检查 → 发现问题再回滚
```

适用于可逆的操作。

### Q3: 如何平衡安全和便利？

**原则：**
- **高风险操作**：严格检查（如删除、覆盖、执行命令）
- **低风险操作**：宽松检查或不检查（如读取文件）
- **开发环境**：适度放宽
- **生产环境**：严格执行

**实现策略：**
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "type": "prompt",
        "prompt": "根据环境调整检查严格度：\n- 开发环境：只检查严重安全问题\n- 测试环境：检查中等以上安全问题\n- 生产环境：检查所有安全问题\n\n当前环境：$ENVIRONMENT\n\n操作：$TOOL_INPUT"
      }
    ]
  }
}
```

## 十一、安全门最佳实践

### 9.1 设计原则

**SMART 原则：**

- **S**pecific（具体的）：明确检查什么
- **M**easurable（可衡量的）：有明确的判断标准
- **A**ctionable（可执行的）：能给出具体建议
- **R**elevant（相关的）：与项目安全相关
- **T**ime-bound（有时限的）：设置合理的超时

### 9.2 实施步骤

**步骤 1：风险评估**
- 识别项目面临的主要安全风险
- 确定优先级（哪些风险最可能造成损失）

**步骤 2：制定规则**
- 针对高优先级风险制定检查规则
- 规则要具体、可执行

**步骤 3：配置 Hook**
- 选择合适的 Hook 类型
- 编写清晰的提示词

**步骤 4：测试验证**
- 用真实场景测试
- 收集误报和漏报

**步骤 5：持续改进**
- 根据反馈优化规则
- 定期更新安全知识库

### 9.3 文档化

为每个安全门规则编写文档：

```markdown
## 规则名称：防止 SQL 注入

### 检查内容
检测代码中是否存在 SQL 注入风险

### 触发条件
当 Claude 写入包含 SQL 查询的代码时

### 判断标准
❌ 违规：字符串拼接 SQL 语句
✅ 合规：使用参数化查询或 ORM

### 修复建议
将 "SELECT * FROM users WHERE id = " + userId
改为 "SELECT * FROM users WHERE id = ?" (参数化查询)

### 示例代码
[好代码示例 vs 坏代码示例]
```

## 附录 A：常见安全漏洞速查表

### A.1 SQL 注入

**危险模式：**
```python
# ❌ 字符串拼接 SQL
query = "SELECT * FROM users WHERE id = " + user_id
```

**安全做法：**
```python
# ✅ 参数化查询
query = "SELECT * FROM users WHERE id = ?"
db.execute(query, (user_id,))
```

**检测要点：**
- SQL 语句中包含变量拼接
- 使用 f-string 或 `+` 连接 SQL
- 未使用 ORM 或参数化查询

### A.2 XSS（跨站脚本攻击）

**危险模式：**
```javascript
// ❌ 直接渲染用户输入
res.send(`<div>${userInput}</div>`);
```

**安全做法：**
```javascript
// ✅ 转义后渲染
const escapeHtml = require('escape-html');
res.send(`<div>${escapeHtml(userInput)}</div>`);
```

**检测要点：**
- innerHTML、dangerouslySetInnerHTML
- document.write
- 模板字符串中的用户输入

### A.3 命令注入

**危险模式：**
```javascript
// ❌ 拼接命令参数
exec(`git clone ${repoUrl}`);
```

**安全做法：**
```javascript
// ✅ 使用参数数组
await execFileNoThrow('git', ['clone', repoUrl]);
```

**检测要点：**
- exec、execSync 中的字符串拼接
- os.system 调用
- shell: true 选项

### A.4 代码注入

**危险模式：**
```javascript
// ❌ eval 执行动态代码
const result = eval(userCode);
```

**安全做法：**
```javascript
// ✅ 使用 Function 构造函数（仍需沙箱）
const safeResult = new Function('return ' + userCode)();
```

**检测要点：**
- eval()
- new Function()
- setTimeout/setInterval 中的字符串

### A.5 不安全的反序列化

**危险模式：**
```python
# ❌ pickle 反序列化不可信数据
import pickle
data = pickle.loads(untrusted_data)
```

**安全做法：**
```python
# ✅ 使用 JSON
import json
data = json.loads(safe_data)
```

**检测要点：**
- pickle.loads / pickle.load
- yaml.load（未指定 Loader）
- 其他语言的类似反序列化 API

### A.6 硬编码凭证

**危险模式：**
```python
# ❌ 硬编码密钥
API_KEY = "sk-1234567890abcdef"
DB_PASSWORD = "admin123"
```

**安全做法：**
```python
# ✅ 从环境变量读取
import os
API_KEY = os.getenv('API_KEY')
DB_PASSWORD = os.getenv('DB_PASSWORD')
```

**检测要点：**
- 代码中的长字符串（可能是密钥）
- 配置文件中的明文密码
- 提交到版本控制的 .env 文件

### E.1 Hookify 插件 - 自然语言规则系统

**位置：** `plugins/hookify/`

**Hook 配置：** `hooks/hooks.json`
```json
{
  "description": "Hookify plugin - User-configurable hooks from .local.md files",
  "hooks": {
    "PreToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/pretooluse.py",
            "timeout": 10
          }
        ]
      }
    ],
    "PostToolUse": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/posttooluse.py",
            "timeout": 10
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/stop.py",
            "timeout": 10
          }
        ]
      }
    ],
    "UserPromptSubmit": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "python3 ${CLAUDE_PLUGIN_ROOT}/hooks/userpromptsubmit.py",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

**核心特色：**

1. **四钩子架构**
   - PreToolUse: 工具使用前检查用户定义的规则
   - PostToolUse: 工具使用后评估结果
   - Stop: 任务完成前验证
   - UserPromptSubmit: 用户提交提示词时处理

2. **自然语言规则**
   - 用户在 `.claude/*.local.md` 文件中定义规则
   - 无需编程，用 Markdown 编写即可
   - AI 理解规则语义并自动执行

3. **规则示例** (`console-log-warning.local.md`)：
   ```markdown
   ---
   event: file
   when: after
   action: warn
   ---
   
   如果 Claude 添加了 console.log 语句进行调试，提醒他应该在提交前移除。
   ```

**工作流程：**
```
用户操作 → Hookify Hook 触发 → 读取所有.local.md 文件 
→ AI 理解规则语义 → 匹配当前操作 → 执行规则动作
```

**与 security-guidance 对比：**

| 特性 | security-guidance | hookify |
|------|------------------|--------|
| **规则定义** | Python 代码 | Markdown 文本 |
| **灵活性** | 固定规则 | 用户自定义 |
| **开发成本** | 需要编程 | 只需文字描述 |
| **适用场景** | 通用安全检查 | 个人/团队定制规则 |

### E.5 设计模式总结

通过分析这些插件，我们可以总结出几种常见的 Hook 设计模式：

#### 模式 1：安全防护型（Security Guidance）
- **目的**：预防危险操作
- **Hook 类型**：PreToolUse（事前检查）
- **实现方式**：Command Hook + Python 脚本
- **特点**：严格规则、快速响应、会话状态管理

#### 模式 2：教学指导型（Explanatory/Learning）
- **目的**：教育和引导
- **Hook 类型**：SessionStart（初始化设置）
- **实现方式**：Command Hook + Shell 脚本
- **特点**：注入系统提示、改变行为模式

#### 模式 3：灵活定制型（Hookify）
- **目的**：用户自定义规则
- **Hook 类型**：多种事件（Pre/Post/Stop/UserPrompt）
- **实现方式**：Command Hook + Python + AI 理解
- **特点**：自然语言规则、高度可配置

#### 模式 4：用户体验型（Ralph Wiggum）
- **目的**：增强趣味性
- **Hook 类型**：Stop（任务完成时）
- **实现方式**：Command Hook + Shell 脚本
- **特点**：轻量级、创意性、个性化
